# Отчёт по ДЗ №1

## 1. Цель работы

Цель работы — сравнить два подхода к созданию небольшого веб-приложения с помощью одной и той же языковой модели:

1. прямой запрос на генерацию готового приложения;
2. подход через предварительную подготовку спецификации, проектных документов и плана реализации.

В обоих случаях создавался автономный мини-трекер учебных задач. Приложение должно работать в браузере из одного HTML-файла без установки библиотек, использования CDN, сервера и внешних API.

## 3. Подход 1 — прямой запрос

### 3.1. Описание подхода

В первом чате модели сразу был отправлен запрос на создание готового автономного HTML-приложения. Предварительные документы, требования в формате MUST и сценарии WHEN/THEN не создавались.

Модель сразу вернула полный HTML-код трекера.

Первый результат сохранён в файле:

`tracker-v1-initial.html`

После ручной проверки модели был отправлен дополнительный запрос на исправление обнаруженных ошибок. Исправленная версия сохранена в файле:

`tracker-v1.html`

Полный диалог сохранён в:

`chat-v1.md`

### 3.2. Обнаруженные проблемы

В первой реализации были обнаружены две функциональные ошибки.

#### Ошибка 1. Неверный расчёт прогресса

Прогресс рассчитывался по количеству выполненных задач, а не по сумме часов выполненных задач.

При трёх начальных задачах одна задача была выполнена, поэтому приложение показывало приблизительно 33%. По требованиям результат должен был равняться:

2 / 8 × 100% = 25%.

После выполнения задачи «Практика» приложение показывало приблизительно 67%, потому что были выполнены две задачи из трёх. Правильный результат по часам:

(2 + 4) / 8 × 100% = 75%.

#### Ошибка 2. Некорректная проверка шага часов

Приложение принимало значение `5.24`, хотя допустимы только значения от `0.5` до `24` включительно с шагом `0.5`.

Допустимыми являются, например:

- `0.5`;
- `1`;
- `1.5`;
- `2`;
- `24`.

Значение `5.24` не соответствует шагу `0.5` и должно отклоняться.

### 3.3. Исправление

В том же чате модели было явно сообщено о двух найденных ошибках и приведена правильная формула прогресса.

Модель вернула обновлённый HTML-код. После исправления:

- прогресс стал рассчитываться по часам;
- начальное значение стало равно 25%;
- после выполнения «Практики» прогресс стал равен 75%;
- значение `5.24` стало отклоняться;
- остальные возможности приложения сохранились.

Количество запросов к модели в первом подходе: 2.

## 4. Подход 2 — спецификация перед реализацией

### 4.1. Описание подхода

Во втором чате код не запрашивался сразу. Сначала модели было предложено подготовить четыре документа:

- `proposal.md`;
- `specs/tracker/spec.md`;
- `design.md`;
- `tasks.md`.

В документах должны были быть определены:

- цель и границы проекта;
- обязательные требования;
- сценарии WHEN/THEN;
- структура данных;
- формула расчёта прогресса;
- правила проверки формы;
- порядок реализации;
- план ручных проверок.

Первые варианты документов сохранены в папке:

`drafts`

Исправленные итоговые документы сохранены в основной структуре проекта.

### 4.2. Проверка первоначальных документов

При проверке первых документов были обнаружены следующие недочёты:

1. Не во всех документах присутствовал фильтр «Готовые».
2. В `proposal.md` не были явно указаны функции, не входящие в проект: сервер, аккаунты, синхронизация и внешние API.
3. В `tasks.md` этапы не были выстроены в требуемом порядке: данные → расчёты → интерфейс → тесты → ручная проверка.

До начала реализации модели был отправлен отдельный запрос на исправление документов.

После исправления документы стали согласованными:

- во всех применимых местах появились три фильтра: «Все», «Активные» и «Готовые»;
- были явно определены границы проекта;
- задачи реализации были расположены в логическом порядке;
- пункты чек-листа не были преждевременно отмечены выполненными.

### 4.3. Реализация

После согласования документов модели был отправлен отдельный запрос на создание `tracker-v2.html` строго по утверждённым требованиям.

Первый полученный вариант реализации сохранён как:

Так как при ручном тестировании функциональные ошибки обнаружены не были, итоговая версия `tracker-v2.html` совпадает с первоначальной реализацией.

Полный диалог второго подхода сохранён в:

Количество запросов к модели во втором подходе: 3:

1. создание документов;
2. исправление документов;

## 5. Методика ручного тестирования

Обе версии проверялись по одинаковым основным сценариям.

### T1. Проверка начального состояния

Проверялось наличие трёх исходных задач:

- «Чтение» — 2 часа, выполнено;
- «Практика» — 4 часа, активно;
- «Повторение» — 2 часа, активно.

Ожидаемая сводка:

- всего 8 часов;
- выполнено 2 часа;
- прогресс 25%.

### T2. Переключение статуса задачи

Задача «Практика» отмечалась выполненной.

Ожидаемый результат:

- всего 8 часов;
- выполнено 6 часов;
- прогресс 75%.

### T3. Проверка фильтров

При исходном состоянии включался фильтр «Активные».

Ожидалось, что в списке останутся:

- «Практика»;
- «Повторение».

При этом общая сводка не должна зависеть от фильтра и должна оставаться равной:

- всего 8 часов;
- выполнено 2 часа;
- прогресс 25%.

Также проверялись фильтры «Все» и «Готовые».

### T4. Проверка формы

Проверялись недопустимые значения:

- пустое название;
- название из пробелов;
- пустое поле часов;
- отрицательное значение;
- `0`;
- `5.24`.

Проверялись допустимые значения:

- `0.5`;
- `2`.

Для ошибочного ввода проверялось, что:

- новая задача не добавляется;
- рядом с соответствующим полем появляется сообщение;
- введённые пользователем данные сохраняются в форме.

### T5. Удаление всех задач

Все задачи последовательно удалялись.

Ожидаемый результат:

- всего 0 часов;
- выполнено 0 часов;
- прогресс 0%;
- отсутствуют значения `NaN` и `Infinity`;
- отображается сообщение о пустом списке.

### T6. Проверка узкого экрана

Страница проверялась в инструментах разработчика браузера при ширине области просмотра 390 px.

Проверялось, что:

- текст остаётся читаемым;
- поля и кнопки помещаются в доступную ширину;
- элементы не перекрываются;
- горизонтальная прокрутка отсутствует.

## 7. Сравнение подходов

### 7.1. Прямой подход

Преимущества:

- готовый код был получен быстрее;
- потребовался только один начальный запрос;
- подход удобен для небольшого прототипа.

Недостатки:

- модель неверно интерпретировала понятие процента выполнения;
- отсутствовала строгая фиксация формулы до реализации;
- проверка шага часов была реализована недостаточно строго;
- ошибки пришлось обнаруживать во время ручного тестирования;
- потребовался дополнительный запрос на исправление.

### 7.2. Подход через спецификацию

Преимущества:

- формула прогресса была зафиксирована до написания кода;
- были явно заданы граничные и ошибочные случаи;
- фильтры и их влияние на сводку были описаны отдельно;
- пустое состояние было определено заранее;
- была зафиксирована адаптация под ширину 390 px;
- итоговая реализация прошла основные ручные проверки без исправления кода.

Недостатки:

- потребовалось больше запросов;
- подготовка и проверка документов заняли больше времени;
- первоначальные документы тоже потребовали уточнения;
- объём текстовых материалов оказался значительно больше.

## 8. Ограничения эксперимента

- Для каждого подхода выполнен только один основной прогон, поэтому результат не доказывает универсальное преимущество одного подхода.
- Точное активное время отдельно не измерялось. Интерфейс не показывает точное количество входных и выходных токенов и денежную стоимость, поэтому эти показатели указаны как «нет данных».
- Вариант A использует спецификацию в формате OpenSpec, но OpenSpec CLI не запускался.
- Проверки выполнялись вручную в одном браузере; результат не доказывает одинаковое поведение во всех браузерах.
- Сохранение через localStorage не являлось обязательным требованием. Его поведение при открытии через file:// может различаться между браузерами и профилями.

## 9. Вывод

Эксперимент показал, что прямой запрос позволяет быстрее получить работающий прототип, но повышает риск неоднозначной интерпретации требований. В данном случае модель неверно поняла способ расчёта прогресса и недостаточно строго проверила шаг значения часов.

Подход через спецификацию потребовал больше подготовительной работы и отдельного исправления документов. Однако ошибки и неоднозначности были устранены до реализации. В результате первая версия кода, созданная после согласования спецификации, прошла основные ручные проверки без дополнительного запроса на исправление HTML.

Для маленьких и некритичных прототипов прямой подход может быть быстрее. Если важны точные формулы, граничные случаи, согласованность требований и воспроизводимая проверка результата, предварительная спецификация оказывается надёжнее.
